# database-migration-safety-review

## Overview
Reviews a proposed schema migration for safety and reversibility before it
ships, and returns a written risk assessment with a recommended safer
rewrite where one is needed. The one job it owns: catch a
production-locking or irreversible migration on paper, before anyone runs
it. This skill is advisory and review-only — it does not execute DDL, and
it does not assume write access to the database being discussed.

## When to use
- A migration diff (hand-written or autogenerated by an ORM/migration tool)
  is open for review before merge.
- Someone asks whether a specific `ALTER TABLE` is safe to run against a
  live table.
- A migration needs a lock-duration or blast-radius estimate before a
  maintenance window is scheduled.
- A prior migration has no documented rollback and one needs to be
  reviewed or written before the next deploy.

## Workflow
1. **Enumerate every statement in the diff** and classify each by type:
   `ADD COLUMN`, `DROP COLUMN`, `ALTER COLUMN TYPE`, `ADD CONSTRAINT`,
   `RENAME`, `CREATE INDEX`, `DROP TABLE`, and so on. Review statement by
   statement — a migration with five statements can have one safe step and
   one dangerous one.
2. **Classify each statement's risk:**
   - **Low-risk (additive):** a new nullable column, a new table, an index
     built with `CONCURRENTLY`. These typically do not block reads or
     writes on the existing structure.
   - **High-risk (rewrites or locks):** adding a column with a non-null
     default that forces a table rewrite on some engines, changing a
     column's type, adding a `CHECK`/`NOT NULL`/foreign-key constraint
     without a `NOT VALID` staging step, renaming a column or table a
     running application still references, or dropping anything live code
     reads.
3. **Estimate lock duration and blast radius for every high-risk
   statement.** A table-rewriting or full-table-validating operation takes
   an exclusive lock for roughly the time it takes to scan or rewrite the
   table — estimate against the table's row count and current traffic
   pattern, and flag anything likely to run longer than the team's
   acceptable lock window.
4. **Recommend expand/contract over a single destructive step.** For
   anything a running application currently reads or writes, recommend
   splitting into: add the new structure alongside the old one → deploy
   code that dual-writes and backfills → deploy code that reads only the
   new structure → drop the old structure in a later, separate migration.
   A single migration that both adds a new structure and removes the old
   one in the same deploy leaves no safe rollback point.
5. **Check the constraint-staging pattern.** A new `NOT NULL` or foreign
   key on an existing table should be added as `NOT VALID` (or the
   engine's equivalent), backfilled/validated, then validated in a
   separate, fast, metadata-only step — not as one locking statement.
6. **Check idempotency.** The migration should be safe to re-run or resume
   after a partial failure: `IF NOT EXISTS` / `IF EXISTS` guards, no
   assumption of a clean starting state, and no dependency on the
   migration having run exactly once already.
7. **Confirm a rollback path.** Either a `down`/reverse migration exists
   and restores the prior schema exactly, or the review explicitly flags
   the migration as irreversible and confirms a backup or snapshot covers
   it before the destructive step runs.
8. **Produce the risk memo, not a run.** Output a statement-by-statement
   table: risk level, estimated lock duration/impact, and the recommended
   safer rewrite for anything high-risk. Hand the memo back to the
   migration's author or the team that owns execution — this skill's
   output is the review, never the applied change.

## Checklist / quality gate
- [ ] Every statement in the migration classified low-risk or high-risk,
      individually.
- [ ] Every high-risk statement has an estimated lock duration and a
      recommended safer alternative.
- [ ] Expand/contract recommended for anything a running application
      currently reads or writes, instead of a single-step change.
- [ ] Constraint additions on existing tables reviewed for the
      not-valid-then-validate split.
- [ ] Idempotency confirmed (safe to re-run after a partial failure).
- [ ] Rollback path confirmed, or the migration is explicitly flagged as
      irreversible with backup coverage noted.
- [ ] The output is a written risk memo — no DDL was executed as part of
      this review.

## Composition
Reviews the output `write-database-migration-with-rollback` hands off (a
forward/rollback migration pair) — this skill is the gate that runs before
merge, not a replacement for authoring one. Pulls
evidence — table size, current traffic, existing lock contention — from
`read-only-diagnostic-query-pack` to back the lock-duration estimate.
Consumes fixes proposed by `index-strategy-design` when the migration under
review is an index change. Hands the final go/no-go and the actual
execution back to a human approver or the deployment system that owns
write access — that decision and that DDL run stay outside this skill.
