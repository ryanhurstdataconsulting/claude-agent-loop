# write-database-migration-with-rollback

## Overview
Produces schema migrations as a forward/rollback pair with an explicit
backward-compatibility plan, so a deploy can always be undone without data
loss and without taking the application offline. The one job it owns: no
migration ships without a tested way back out.

## When to use
- A schema change is requested: new column/table/index/constraint, a type
  change, a rename, or a drop.
- A large table needs a data backfill (populate a new column, reshape data).
- A migration tool's autogenerated diff needs review before it is trusted.
- A prior deploy needs to be rolled back and the existing migration has no
  `down`/rollback step.

## Workflow
1. **Classify the change before writing SQL.** Additive changes (new nullable
   column, new table, new index) are low-risk and can usually ship in one
   step. Anything that changes or removes an existing structure a running
   application still reads (drop column, rename column, change type,
   tighten a constraint, add `NOT NULL` to an existing column) needs the
   **expand/contract** pattern below — never a single-step destructive
   migration against a table live traffic touches.
2. **Expand/contract for anything the running application depends on:**
   - **Expand** — add the new structure alongside the old one (new column,
     new table) without removing anything. Deploy this first; the old code
     path keeps working untouched.
   - **Migrate/dual-write** — deploy application code that writes to both the
     old and new structure, and backfills existing rows into the new one.
   - **Cut over** — deploy application code that reads from the new structure
     only, once the backfill is confirmed complete.
   - **Contract** — drop the old structure in a final migration, only after
     the cutover has been running cleanly for a deploy cycle or two.
   - Each phase is independently deployable and independently reversible —
     that is the entire point of splitting it into four steps instead of one.
3. **Write the rollback (`down`) migration as a first-class artifact, not an
   afterthought.** It should restore the prior schema state exactly. If a
   migration is truly irreversible (an executed `DROP TABLE` with no
   retained data), say so explicitly in the migration's description and
   confirm a backup/snapshot exists before that step runs — do not silently
   ship a no-op `down`.
4. **Backfill large tables in bounded chunks, never a single unbounded
   `UPDATE`.**
   - Batch by primary-key range or a cursor, with a small sleep between
     batches to bound replication lag and lock contention.
   - Make the backfill script idempotent and resumable — a script that can
     be re-run safely after a partial failure, keyed off a "still needs
     backfill" predicate (e.g., `WHERE new_column IS NULL`), rather than one
     that assumes a clean starting state.
   - Run backfills against a replica-lag-aware pace, and add an index to
     support the batch-selection query itself, or the backfill will full-scan
     on every batch.
5. **Add constraints in two steps on a live table.** Adding `NOT NULL` or a
   foreign key directly can lock the table for the duration of a full-table
   validation scan on some engines. Prefer: add the constraint as `NOT VALID`
   (or the engine's equivalent), backfill/validate data, then `VALIDATE`
   the constraint in a separate, fast metadata-only step.
6. **Never reuse a migration's identity after it has shipped.** If a mistake
   is found in an already-applied migration, write a new migration to correct
   it — do not edit and re-run a migration file that has already run in any
   environment, or environments will drift out of sync on what "already
   applied" means.

## Checklist / quality gate
- [ ] A rollback (`down`) migration exists and restores the prior schema
      state, or the migration explicitly documents why it is irreversible
      and what backup covers it.
- [ ] Any change that a running application currently reads or writes uses
      the expand/contract pattern rather than a single destructive step.
- [ ] Backfills run in bounded, resumable, idempotent chunks — never one
      unbounded statement against a large table.
- [ ] New `NOT NULL`/foreign-key constraints on existing tables are added as
      not-valid-then-validate (or the engine equivalent) rather than a single
      locking statement.
- [ ] The migration has been tested against a copy of production-shaped data
      volume, not just an empty local database.
- [ ] No previously applied migration file was edited in place.
